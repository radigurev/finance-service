Statuses (see `docs/README.md` → "Status lifecycle" for the authoritative definitions):
- **Planned** — named in the plan/inventory; no spec file authored yet
- **Drafted** — spec authored; may still change or be dropped; not yet committed
- **Active** — accepted & committed ("will be built to the end; should be implemented"); may be partially or not-yet built
- **Implemented** — code shipped + tests pass + in force (may carry explicit `Deferred:` notes for later-phase sub-items)
- **Deprecated** — retired or superseded; no longer in force

- **Shipped defects found by the Payments spec review (round 2, 2026-08-05 — RECORDED, not fixed; no code and no system spec changed):** `CHG-FIX-004` (`docs/changes/CHG-FIX-004-journal-reversal-bypasses-period-guard.md`, Status `Proposed`) — `JournalEntryService.ReverseInTransactionAsync` reuses `original.EntryDate` and stamps the offsetting entry `Posted` directly via `StampPosted`, and `PostingPeriodWorkflowGuard` returns success unless `TargetState == Posted` (the transition on the original is `Posted → Reversed`), so ANY reversal — journal entry, invoice, or payment — can insert a `Posted` entry into a CLOSED period; affects `SDD-FIN-002`/`SDD-FIN-004`/`SDD-INV-001`/`SDD-PAY-001` (SDD-PAY-001 §2.7 adds its own endpoint-level period pre-check as a PARTIAL mitigation; the generic hole remains). `CHG-FIX-005` (`docs/changes/CHG-FIX-005-confirmed-invoice-cancel-orphans-journal-entry.md`, Status `Proposed`) — `SDD-INV-001`'s `Confirmed → Cancelled` transition has the window SDD-PAY-001 closed by removing it: `InvoiceConfirmedEvent` is already in flight, the Journal consumer posts unconditionally, and `Cancelled` is terminal, so a posted entry is left with no supporting document; affects `SDD-INV-001`/`SDD-AUDIT-001` (changing a shipped, tested lifecycle needs its own batch).
- **Shipped defect found by the Payments spec review (round 3, 2026-08-05 — FIXED IN THIS BATCH: code + tests + a one-line record in the owning system spec):** `CHG-FIX-006` (`docs/changes/CHG-FIX-006-idempotency-filter-swallows-consumer-failures.md`, Status `Implemented`) — `IdempotencyFilter<T>.Send` claimed `finance:processed:{MessageId}` (Redis `SETNX`, 7-day TTL) and forwarded to the downstream pipe with NO try/catch, while `MessagingServiceCollectionExtensions` registers `bus.UseMessageRetry(...)` BEFORE `bus.UseFinanceIdempotency(context)` (retry is the OUTER filter) — so a throwing consumer's first redelivery re-entered the filter, matched the filter's OWN claim, logged "Duplicate message skipped" and returned success: the message was silently ACKed and NOTHING ever reached `<queue>_error`. Blast radius = every shipped consumer (the four `SDD-INT-WH-001` Warehouse consumers, `InvoiceConfirmedEventConsumer`, `InvoicePostedEventConsumer`, the six `SDD-EVTLOG-001` consumers) and every retry-then-dead-letter recovery contract in the platform. Fix: a failed consume `KeyDeleteAsync`es the claim and rethrows (bare `catch { … throw; }`, stack preserved); the duplicate short-circuit and the Redis-failure fall-open are unchanged. No MUST changed — `SDD-INFRA-006` §2.3/§2.4/§4 already mandated this behavior, so the spec records the fix in its Status line only. It is a hard PREREQUISITE of the retry/DLQ wording in `SDD-PAY-001` §2.5/§2.18, `SDD-PAY-002` §2.3/§2.14 and `SDD-INV-001` §2.13/§2.15 (each cites it). Code: `src/Infrastructure/Messaging/Finance.Infrastructure.Messaging/Filters/IdempotencyFilter.cs`; tests: two NEW `[Unit]` in `src/Infrastructure/Finance.Infrastructure.Stateful.Tests/Messaging/IdempotencyFilterTests.cs` — `Send_DownstreamPipeThrows_DeletesProcessedKeyAndRethrowsOriginalException`, `Send_GenuineDuplicateAfterSuccessfulConsume_DoesNotInvokeNextAgain_AndKeepsClaim`.
- **Round-3 `§`-reference corrections to the two RECORDED-only defects (both still `Proposed`; no code, no system spec changed):** `CHG-FIX-004` §5 now cites `SDD-PAY-001` **§2.18** (not §2.13, which is "Posting-rule templates & seeding") for the *"reversing a payment whose original period has closed"* edge case; `CHG-FIX-005` now cites `SDD-INV-001` **§6.1** (not §6.2) for `Cancel_ConfirmedInvoice_TransitionsToCancelled_KeepsDocumentNumber` in all five places (§2 evidence #11, §4, §7 rule 7, the §8 affected-specs table, §12) — matching the shipped test's own XML doc.
