## 1. Context & Scope

This spec defines the **`Invoice` aggregate** and its **lifecycle**: the state machine that moves an invoice through `Draft → Confirmed → Posted` (plus `Cancelled` and the `Reversed`/credit-note correction path), the side effects each transition triggers, the country-aware tax computation that produces its totals, and the handshake by which a confirmed invoice becomes a posted journal entry.

A single aggregate `Invoice` represents all four financial documents — **Purchase Invoice**, **Sale Invoice**, **Credit Note**, **Debit Note** — discriminated by a `DocumentType` enum and a `Direction` (`AP` payable / `AR` receivable). The header carries totals; the `invoice_lines` child collection carries the per-line breakdown. This is the documents tier of the platform (FINANCE-MICROSERVICES-PLAN §2, service #5).

Three principles govern the lifecycle, mirroring SDD-FIN-002:
1. **Confirmed/Posted is immutable (SDD-AUDIT-001).** Once an invoice is `Confirmed` it has a legally-issued gapless document number and MUST NEVER have its header or lines edited. A correction is made by issuing a **Credit Note** (to reduce/cancel) or a **Debit Note** (to increase) — never by UPDATEing the confirmed/posted row. A confirmed invoice MAY be `Cancelled` (voided) only before posting; a posted invoice is corrected only by a note (`Reversed` path, §2.7).
2. **Numbering is gapless and country-formatted.** The gapless document number (`ISequenceGenerator`, SDD-INFRA-003) is assigned at **Confirm** — its format comes from `ICountryStrategy.GenerateDocumentNumber` (SDD-CTRY-001) per document type (`PINV`/`SINV`/`CN`/`DN`).
3. **Posting is delegated, never reimplemented.** The Invoice service does NOT build double-entry lines, number journal entries, or write GL. On confirm it publishes `InvoiceConfirmedEvent` through the transactional outbox; the **Journal** service consumes it and posts the journal entry via the Posting Engine (SDD-FIN-006) using posting rules (SDD-FIN-002/SDD-FIN-006 own the JE entirely). The invoice moves to `Posted` and stores the resulting `JournalEntryId` when the Journal service publishes back the dedicated `InvoicePostedEvent` (§2.5). A dedicated back-event is used rather than the generic `JournalEntryPostedEvent` (which is published for every journal entry and is already consumed by the EventLog archive); a dedicated event keeps the invoice→posting correlation explicit and unambiguous and avoids fragile routing/matching of a multi-purpose event.

**Tax computation goes through the country strategy.** Line and document totals (net, tax, gross) MUST be computed via `ICountryStrategy` tax methods and rounded via `ICountryStrategy.ApplyTaxRounding`, using `decimal` only (SDD-FIN-005). The core invoice code MUST remain country-agnostic — it MUST NOT hard-code a VAT rate, a rounding rule, or a number format. This spec GROWS the `ICountryStrategy` interface (currently three members per SDD-CTRY-001) with the tax + document-number members (§5).

**ISA-95 classification.** An `Invoice` is an ISA-95 **Level 4 (Business Planning & Logistics)** financial **Document** (ISA-95 / IEC 62264 Part 1, §5). The **confirm**, **post**, **cancel**, and **note/reverse** operations are Level-4 business transactions that change the document's recorded state; each MUST emit an **immutable domain event** for state changes (`InvoiceConfirmedEvent`, `InvoiceCancelledEvent`, and — added by the settlement amendment, §2.7/§2.11 — `InvoiceReversedEvent`; the posted state is reflected by the dedicated `InvoicePostedEvent` published by the Journal service) and an immutable audit row (SDD-AUDIT-001). Each `InvoiceLine` is the Level-4 transaction-line / component of the document (parity with `JournalEntryLine` under SDD-FIN-001/-002), carrying the per-line net/tax/gross breakdown that rolls up to the header totals. The `invoice_status_history` rows are append-only Level-4 audit sub-records. No Level-3 (MES) activity is modelled. The counterparty (customer/supplier) is Warehouse-owned Level-4 master data referenced by GUID, NOT a foreign key (cross-service joins are forbidden, Plan §8).

**Scope — covered (v1):**
- The `Invoice` aggregate (header `invoices`, child `invoice_lines`) with `DocumentType` (`PurchaseInvoice` | `SaleInvoice` | `CreditNote` | `DebitNote`), `Direction` (`AP` | `AR`).
- The `Draft → Confirmed → Posted` state machine via `IWorkflowEngine<Invoice>`, plus `Cancelled` (from `Draft`/`Confirmed`) and the Credit/Debit-Note correction path for a `Posted` invoice (§2.7).
- CRUD on drafts: create (manual user-entered AND system-created from Warehouse events — SDD-INT-WH-001), update draft, get, list (filtered/paged), cancel.
- Country-aware tax computation + rounding via `ICountryStrategy`; totals reconciliation (lines sum to header; net + tax = gross to the cent).
- Confirm: gapless country-formatted document number, totals freeze, audit-first → outbox `InvoiceConfirmedEvent`, status-history append — all atomic.
- The Confirm→Post handshake with the Journal service (§2.5) and the inbound `InvoicePostedEvent` consumer that links `JournalEntryId` and moves `Confirmed → Posted`.
- Immutability enforcement on `Confirmed`/`Posted` invoices; corrections via Credit/Debit Note.
- RBAC, correlation, audit, outbox, no-caching (transactional data).
- **Settlement mirror (added 2026-08-05 by the SDD-PAY-002 amendment — shipped in Batch 17):** the invoice-side `SettledAmount` + derived `SettlementStatus` (the shared enum owned by SDD-PAY-002 §2.8), maintained by ORDERED, idempotent consumers of SDD-PAY-002's allocation events (§2.15) that keep the `LastSettlementAppliedAt` ordering token (§2.14); the frozen `ExchangeRate` booking rate that sources `InvoiceConfirmedEvent.BookingExchangeRate` (§2.14/§2.15); and the best-effort `INVOICE_HAS_SETTLEMENTS` cancel guard (§2.6). Settlement state is ORTHOGONAL to the lifecycle above and MUST NEVER drive a transition (§2.14).
- **`InvoiceReversedEvent` (added 2026-08-05 by the SDD-PAY-002 amendment — shipped in Batch 17):** the `Posted → Reversed` transition of §2.7 MUST publish a new outbox event so downstream sub-ledgers learn that a posted document has been voided by a fully-offsetting note (§2.7/§2.11). The transition itself is unchanged — only the publish is added.

**Scope — excluded (DEFERRED):**
- **The journal entry itself** — drafting/numbering/balancing/GL of the JE is SDD-FIN-002 / SDD-FIN-006 / SDD-FIN-003. This spec only triggers it.
- **The Warehouse event consumers** that create system drafts — SDD-INT-WH-001 (sibling spec, same batch). This spec defines the create path they call; it does NOT define the event contracts or the consumers.
- **Payment allocation itself** (the `PaymentAllocation` match rows, the allocation invariant chain, the Payments-local `InvoiceOpenItem` projection, realized FX) — SDD-PAY-002; and **AP/AR aging / counterparty balances / outstanding-item listing** — SDD-PAY-003. Only the invoice-side settlement MIRROR is in scope here (§2.14/§2.15); this spec MUST NOT reimplement or second-guess the allocation rules.
- **VAT journals / regulatory НАП export** of invoices — SDD-RPT-003 / SDD-INT-NAP-001.
- **FX rate resolution** — a non-base-currency invoice supplies its rate (frozen at creation into the `ExchangeRate` column, §2.14); automatic rate lookup is SDD-FIN-005. v1 SHOULD assume a base-currency context.
- **Multi-line tax codes / mixed VAT rates per line beyond a single `TaxRate` per line** — the line carries one `TaxRate`; richer tax-code matrices are SDD-CTRY-BG-001.
- **Approval / maker-checker** between `Draft` and `Confirmed` — future `CHG-FEAT-*`.

## 2. Behavior

> **Service/controller contract (SDD-INFRA-009).** `InvoiceService` MUST inherit `SearchableServiceBase<Invoice, InvoiceDto, InvoicesDbContext>` (and `BaseEntityService<InvoicesDbContext>`). Every public method MUST return `Result` / `Result<T>` — never `null`, never a thrown exception for a business outcome. `InvoicesController` inherits `BaseApiController` and translates every result via `ToActionResult(...)`. State transitions MUST go through `IWorkflowEngine<Invoice>` (SDD-INFRA-008); the service owns `SaveChanges` / `RowVersion` / status-history inside the outbox transaction. `CancellationToken` MUST be threaded controller → service → DB / sequence / publish.

### 2.1 State machine (MUST — SDD-INFRA-008)
- `Invoice` MUST be a workflow aggregate with these states and `AllowedNextStates`:
  - `Draft` → { `Confirmed`, `Cancelled` } (and a `Draft` MAY be **deleted/updated** — a removal/edit, not a transition).
  - `Confirmed` → { `Posted`, `Cancelled` }.
  - `Posted` → { `Reversed` } (a posted invoice is corrected only by the Credit/Debit-Note path, §2.7; the `Reversed` flag records that a correcting note offsets it).
  - `Cancelled` → { } (terminal).
  - `Reversed` → { } (terminal).
- Any transition not in `AllowedNextStates` MUST be rejected by the engine and surfaced as `INVALID_INVOICE_STATE_TRANSITION` (the domain alias for the engine's generic `INVALID_STATE_TRANSITION`, SDD-INFRA-008 §4, mirroring SDD-FIN-002 §2.1).
- A new invoice MUST be created in `Draft` (§2.3).

### 2.2 Workflow guards & ordering (MUST)
- The `Draft → Confirmed` transition MUST run, in order:
  1. The full validation surface (§3): at least one line, every line valid, totals reconciled (lines sum to header; net + tax = gross to the cent), counterparty present, currency valid, dates valid.
  2. The **period-open guard** for the invoice `IssueDate` — a closed/locked period MUST short-circuit with `INVOICE_PERIOD_CLOSED`. This reuses the same period-status seam SDD-FIN-002 §2.7 uses (`IPostingPeriodGuard`-equivalent backed by SDD-FIN-004); until SDD-FIN-004's lookup is reachable from this service the default is always-open.
- A guard failure MUST short-circuit with no side effects (no number burned, no event, no audit row) and surface as `Result.Failure(...)` carrying the failing guard's code.

### 2.3 Create draft (MUST)
- `POST /api/v1/invoices` MUST create an `Invoice` in `Draft` with the caller-supplied `DocumentType`, counterparty reference, currency, dates, and lines. Requires `finance.invoice:create`.
- The SAME domain create path MUST serve both **manual** (user-entered via the endpoint) and **system-created** drafts (from Warehouse events — SDD-INT-WH-001). SDD-INT-WH-001's consumers MUST call this service method, NOT a parallel creation path.
- `Direction` MUST be derived from `DocumentType` and frozen: `SaleInvoice`/`DebitNote` → `AR`; `PurchaseInvoice`/`CreditNote` → `AP`. (A Credit Note reduces what a customer owes when paired with a sale, but in v1 `Direction` follows the table above; the pairing/offset is the note's `CorrectsInvoiceId` link, §2.7.)
- `DocumentNumber` MUST remain NULL while `Draft` — the gapless number is assigned only at Confirm (§2.4).
- Totals (`NetTotal`, `TaxTotal`, `GrossTotal`) MUST be computed on create from the lines via `ICountryStrategy` (§2.8) and stored; they MUST reconcile (§3.2) before the draft is saved — but a draft MAY be saved even if it would not yet confirm (e.g. zero lines) ONLY when created by a system event that will be completed later; a **manual** create MUST require ≥ 1 line (`INVOICE_LINES_REQUIRED`).
- `BaseCurrencyCode` MUST be set from `ICountryStrategy.BaseCurrencyCode` and frozen on the invoice.
- `CorrelationId` MUST be captured from `ICorrelationIdAccessor`; `CreatedAt` server-side (`SYSDATETIMEOFFSET()`); `CreatedBy` from the authenticated principal (or the system identity for event-created drafts).
- Draft creation MUST write an audit `Create` row (`BeforeJson = null`). No domain event is published on draft creation.

### 2.4 Confirm (MUST)
- `POST /api/v1/invoices/{id}/confirm` MUST transition a `Draft` invoice to `Confirmed` via `IWorkflowEngine<Invoice>`. Requires `finance.invoice:confirm`.
- The invoice MUST be in `Draft`; otherwise `INVOICE_NOT_DRAFT`.
- On a successful transition the service MUST, within a single SaveChanges/outbox transaction and in this order:
  1. Run the §2.2 guards (full validation + period-open).
  2. Recompute and freeze totals via `ICountryStrategy` (§2.8); re-assert reconciliation (`INVOICE_TOTALS_MISMATCH` if it fails).
  3. Assign `DocumentNumber` from `ISequenceGenerator.NextAsync(<key>, ct)` where `<key>` is the per-document-type sequence key (`PINV`/`SINV`/`CN`/`DN`, SDD-INFRA-003 §2.1) and the FORMAT comes from `ICountryStrategy.GenerateDocumentNumber` (SDD-CTRY-001). The number MUST be allocated inside the same transaction (no burn on rollback — SDD-INFRA-003 §2.4).
  4. Stamp `ConfirmedAt = SYSDATETIMEOFFSET()` and `ConfirmedBy`; set `Status = Confirmed`.
  5. Append the `invoice_status_history` row (`Draft → Confirmed`).
  6. Write an audit `StateChange` row (`EventType = "InvoiceConfirmed"`, `BeforeJson` = draft snapshot, `AfterJson` = confirmed snapshot) **before** the outbox row (audit-first, SDD-AUDIT-001).
  7. Enqueue `InvoiceConfirmedEvent` to the outbox (atomic with the DB write — no `await _bus.Publish` outside the outbox, no try/catch, SDD-INFRA-006), then `SaveChanges` and commit; `RowVersion` increments.
- The load-bearing ordering guarantee is **audit BEFORE outbox** (step 6 before step 7), which `Confirm_RecordsAuditStateChange_BeforeOutboxPublish` (§6.2) pins. The `invoice_status_history` append is a plain child insert in the same transaction, so its position relative to the audit row and the outbox row is unobservable; the enumeration above states it where the shipped `ConfirmInTransactionAsync` performs it (`src/Interfaces/Invoices/Finance.Invoices.API/Services/InvoiceService.cs` — history, then audit, then publish, then save/commit), so the spec and the code read in the same order. The §2.7 reversal path follows the same shape.
- Confirm is NOT on SDD-AUDIT-001's mandatory-`Reason` list (it is a routine issuance), so no `Reason` is required.

### 2.5 Posting handshake — Confirm → Posted (MUST)
- **Decision (chosen, simpler option).** Confirm publishes `InvoiceConfirmedEvent`; the **Journal** service is the authority that posts the journal entry (via the Posting Engine, SDD-FIN-006) and publishes back a **dedicated `InvoicePostedEvent`** carrying the source invoice id, the resulting journal entry id, and the journal entry number; the **Invoice** service consumes that event, stores the resulting `JournalEntryId`, and moves the invoice `Confirmed → Posted`. The Invoice service NEVER posts a journal entry itself. A dedicated back-event is used rather than the generic `JournalEntryPostedEvent` because that event is published for every posted journal entry (not only invoice-originated ones) and is already consumed by the EventLog archive; routing and correlation-matching a multi-purpose event into the Invoice service is fragile, whereas a dedicated event makes the invoice→posting link explicit.
- `InvoiceConfirmedEvent` (§2.11 — the authoritative payload list) MUST carry enough for the Journal-side posting rule to materialize a balanced entry: invoice id, document type, direction, counterparty id, currency, base currency, issue date, the chosen `PostingRuleKey` (derived from `DocumentType` — e.g. `SALE_INVOICE` / `PURCHASE_INVOICE`), and the net/tax/gross amounts. The Journal consumer calls `IPostingEngine.ApplyAsync` with those amounts (SDD-FIN-006 §2.3) — this spec does NOT define the rule materialization.
- **(SDD-PAY-001 duplicate-post hardening — shipped in Batch 17.)** The Journal-side consumer (`src/Interfaces/Journal/Finance.Journal.API/Consumers/InvoiceConfirmedEventConsumer.cs`) MUST stamp the source-document pair `SourceDocumentType = "Invoice"` / `SourceDocumentId = InvoiceId` on every journal entry it posts for an invoice, and when a `Posted` entry already exists for that pair it MUST post NOTHING — no second `ApplyAsync` — and instead RE-PUBLISH `InvoicePostedEvent` for the entry that already exists, so a back-event lost between the two services is recoverable without a second entry. The re-publish carries a FRESH `MessageId` and the source event's `CorrelationId`; the invoice-side `InvoicePostedEvent` consumer is idempotent (see the inbound-consumer bullet below — a replay against an already-`Posted` invoice is a no-op), so the extra back-event is harmless. Gap this closed (verified against the pre-Batch-17 code): the consumer called `IPostingEngine.ApplyAsync` unconditionally on every delivery and the `JournalEntry` (`src/Databases/Finance.Journal.DBModel/Models/JournalEntry.cs`) carried NO source-document reference at all (only `ReversesEntryId`), so it could not detect that an entry for the invoice already existed. `IdempotencyFilter<T>`'s `MessageId` `SETNX` (SDD-INFRA-006) is transport-level dedupe that EXPIRES, so a redelivery after its TTL — or a `finance-journal_error` replay — posted a SECOND balanced entry for one invoice: the trial balance still balanced, this service still read `Posted` with one linked `JournalEntryId`, and the control account was silently overstated by the invoice gross. The two additive `JournalEntry` columns, the Journal migration `20260805174405_AddJournalEntrySourceDocument`, and the UNIQUE FILTERED index over (`SourceDocumentType`, `SourceDocumentId`) that backstops them are OWNED by SDD-PAY-001 §2.5 (whose payment-side consumer carries the identical guard for `("Payment", PaymentId)`); this spec records only the invoice-side obligation and still does NOT define or redefine the journal entry (§1 principle 3). The pair mirrors what the `Invoice` aggregate already does for its Warehouse origins (`Invoice.SourceDocumentType`/`SourceDocumentId`, SDD-INT-WH-001 §2.1.2/§2.1.4). It is ADDITIVE hardening: no posting rule, no event payload, no invoice-side state, and no step of the handshake above changed.
- `POST /api/v1/invoices/{id}/post` (explicit) MUST be the operator-driven equivalent of awaiting the handshake: it MUST verify the invoice is `Confirmed`, and either (a) if the linked `JournalEntryId` is already recorded (the back-event arrived), confirm the `Posted` transition; or (b) if not yet linked, return `INVOICE_NOT_CONFIRMED`/`INVOICE_POSTING_PENDING` so the caller retries. The asynchronous back-event consumer (next bullet) is the primary path; this endpoint is for visibility/manual completion. Requires `finance.invoice:post`.
- The inbound `InvoicePostedEvent` consumer (in `Finance.Invoices.API/Consumers/`) MUST be wrapped in `IdempotencyFilter<T>` (SDD-INFRA-006), MUST match the event to the source invoice by the `InvoiceId` carried on the event, MUST set `JournalEntryId`, stamp `PostedAt`, transition `Confirmed → Posted` via the workflow engine, write an audit `StateChange` (`EventType = "InvoicePosted"`), append status history, and increment `RowVersion` — all in one transaction. A replay MUST be a no-op (the invoice is already `Posted`).
- **Deferred alternative (documented, not chosen):** *optimistic posting* — Confirm could itself post the JE synchronously (call `IPostingEngine.ApplyAsync` across the service boundary) and store `JournalEntryId` immediately, moving straight to `Posted`. Rejected for v1 because it couples the Invoice transaction to the Journal service's availability and breaks the database-per-service / async-mesh boundary (Plan §8). The event-driven handshake keeps the services decoupled and the post resilient (outbox + idempotency). The optimistic path MAY be revisited in a future `CHG-ENH-*` if synchronous posting is required for UX.

### 2.6 Update / cancel draft & confirmed (MUST)
- `PUT /api/v1/invoices/{id}` MUST update a `Draft` invoice only (counterparty, dates, lines). Requires `finance.invoice:create`.
  - An update against a `Confirmed`/`Posted`/`Cancelled`/`Reversed` invoice MUST be rejected with `INVOICE_POSTED_IMMUTABLE` — confirmed and later states are immutable (§2.9).
  - The updated draft MUST recompute totals via `ICountryStrategy` and re-reconcile (§3.2) before persisting.
  - Optimistic concurrency MUST be enforced via the base64 `RowVersion`; a stale token MUST yield `CONCURRENT_MODIFICATION`.
  - An update MUST write an audit `Update` row.
- `POST /api/v1/invoices/{id}/cancel` MUST cancel (void) a `Draft` or `Confirmed` invoice (transition to `Cancelled`). Requires `finance.invoice:cancel`.
  - Cancelling a `Posted`/`Cancelled`/`Reversed` invoice MUST be rejected with `INVALID_INVOICE_STATE_TRANSITION` (a posted invoice is corrected by a note, never cancelled).
  - A non-empty `Reason` MUST be supplied (cancellation voids a numbered document — sensitive); a missing reason MUST yield `INVOICE_CANCEL_REASON_REQUIRED`.
  - **(SDD-PAY-002 settlement amendment — shipped in Batch 17 as `InvoiceSettlementWorkflowGuard`.)** A `Draft`/`Confirmed` invoice that already carries settlements (`SettledAmount > 0.00`, §2.14) MUST NOT be cancelled — the cancel MUST fail with `INVOICE_HAS_SETTLEMENTS` BEFORE the workflow transition, with no audit row and no event. Voiding a document a counterparty has already paid against would orphan the payment's allocation rows, which SDD-PAY-002 §2.6 releases ONLY through an explicit deallocate; the operator MUST deallocate in the Payments service first. This guard MUST run as an `IChainValidator<WorkflowContext<Invoice>>` on the transition to `Cancelled` (SDD-INFRA-007/-008), NOT as a FluentValidation rule (it is stateful).
  - **The `INVOICE_HAS_SETTLEMENTS` guard is BEST-EFFORT, not a hard invariant.** It reads `SettledAmount`, which is an ASYNCHRONOUSLY-fed mirror of the Payments-side allocation rows, and the settlement handshake is deliberately one-way with no synchronous read of the Payments service (§2.15, SDD-PAY-002 §2.10). A cancel that RACES an in-flight allocation — the allocation already committed in `finance_payments` but its event not yet applied here — therefore still passes the guard and CAN orphan an allocation row. This spec MUST NOT claim otherwise: **SDD-PAY-002 is the authority on allocation rows.** Its `InvoiceCancelledEvent` consumer performs the authoritative detection — it checks for `PaymentAllocation` rows on the cancelled `InvoiceId` and, when any exist, emits a structured NLog warning flagging an orphaned settlement for the deferred reconciliation job (SDD-PAY-002 §2.3/§2.14/§7, SDD-OBS-001). The guard's purpose is to stop the ORDINARY operator mistake, not to make the race impossible; closing the race would require a synchronous cross-service read, which Plan §8 forbids.
  - Cancelling a `Confirmed` invoice MUST NOT reuse or release its gapless document number (numbers are gapless and never recycled — НАП); the cancelled row keeps its number with `Status = Cancelled`.
  - Cancel MUST write an audit `StateChange` row (with the `Reason`) and publish `InvoiceCancelledEvent` via the outbox.

### 2.7 Correction of a posted invoice via Credit/Debit Note (MUST — the immutability-preserving correction)
- A `Posted` invoice MUST NEVER be edited or cancelled. To correct it, the operator issues a **Credit Note** (reduces the original) or **Debit Note** (increases it) as a NEW `Invoice` whose `CorrectsInvoiceId` links back to the original.
- The note is a normal invoice document: created as `Draft`, confirmed (its own gapless `CN`/`DN` number + `InvoiceConfirmedEvent` → its own posting), and posted via the same handshake (§2.5). Its posting rule (`CREDIT_NOTE`/`DEBIT_NOTE`) produces the offsetting/augmenting journal entry.
- When a Credit Note that **fully** offsets the original is posted, the original MAY transition `Posted → Reversed` to record that it is fully corrected; a partial note leaves the original `Posted`. The decision (full-offset → `Reversed`) MUST be explicit and recorded in an audit `StateChange` (`EventType = "InvoiceReversed"`) with the linking note id and `Reason`. The original's lines/number MUST NOT be mutated (only the state flag + `RowVersion` + status history).
- **(SDD-PAY-002 settlement amendment — shipped in Batch 17 as `IInvoiceService.MarkReversedAsync`.)** Whenever that `Posted → Reversed` transition occurs, the service MUST enqueue an `InvoiceReversedEvent` (§2.11) to the transactional outbox in the SAME transaction as the state flag, the audit row, and the status-history row — audit-first, then outbox, exactly as confirm (§2.4) and cancel (§2.6) do. The publish is ADDITIVE: it changes no guard, no ordering, and no other effect of the transition. A reversal that is not published is a silent data-integrity hole downstream, because a `Reversed` invoice carries no remaining ledger balance while SDD-PAY-002's `InvoiceOpenItem` projection would keep mirroring it as `Posted` — and SDD-PAY-002 §2.5 admits `Confirmed`/`Posted` open items as legal allocation targets, so real cash could be matched to a voided document while the genuinely open invoice stayed outstanding. SDD-PAY-002 §2.3 registers the consumer that sets the mirrored `InvoiceStatus = Reversed` and §2.5 excludes `Reversed` from the eligibility set (`PAYMENT_ALLOCATION_INVOICE_NOT_ELIGIBLE`). This spec publishes and MUST NOT be called back: the handshake stays one-way (§2.15).
  - **What is NOT changed by this amendment.** The automatic full-offset DETECTION that would trigger the transition remains the §5-deferred sub-item — v1 exposes no offset-driven reversal API and `InvoicesController` has no reverse endpoint (verified), so a posted original still stays `Posted` after a note is issued and the shipped §6.5 tests continue to assert exactly that. What Batch 17 shipped is the event CONTRACT, the publish obligation, and the transition path itself (`MarkReversedAsync`) — so the reversal can never land without the sub-ledger being told, and SDD-PAY-002 registered its consumer in the same batch rather than after the fact. Nothing in production invokes the path yet; the deferred detection is its only intended caller.
- This mirrors SDD-FIN-002 §2.6 reversal: nothing is overwritten; both the original (with its `Reversed` flag) and the note (a separate posted document) persist. It also mirrors SDD-FIN-002's `JournalEntryReversedEvent` (`src/Finance.ServiceModel/Events/Journal/JournalEntryReversedEvent.cs`) at the document tier: reversal is a published state change there too, not a silent flag.

### 2.8 Tax computation & totals (MUST — SDD-CTRY-001 / SDD-FIN-005)
- Each `invoice_line` MUST carry `Quantity`, `UnitPrice`, `TaxRate`, and the derived `LineNet`, `LineTax`, `LineGross`. `LineNet = round(Quantity × UnitPrice)`, `LineTax = ICountryStrategy.ApplyTaxRounding(LineNet × TaxRate)`, `LineGross = LineNet + LineTax`. All arithmetic MUST be `decimal` (`DECIMAL(18,2)` amounts, `DECIMAL(18,6)` rates) — never `double`/`float`.
- Rounding MUST go through `ICountryStrategy.ApplyTaxRounding` — the core MUST NOT inline a rounding mode. Tax-rate validity/lookup MUST go through `ICountryStrategy` (the country owns which rates are legal).
- Document totals MUST be the sum of the line components: `NetTotal = Σ LineNet`, `TaxTotal = Σ LineTax`, `GrossTotal = Σ LineGross`, and `GrossTotal = NetTotal + TaxTotal` MUST hold to the cent. A mismatch MUST yield `INVOICE_TOTALS_MISMATCH`.
- Totals MUST be (re)computed by the service from the lines — a client-supplied total MUST be ignored or validated against the computed value (never trusted blindly).

> **`INVOICE_TOTALS_MISMATCH` is a defensive (fail-fast) invariant, unreachable through the v1 service paths.** Because the service ALWAYS recomputes the header totals from the lines via `InvoiceTotalsCalculator` (`NetTotal = Σ LineNet`, `TaxTotal = Σ LineTax`, `GrossTotal = Σ LineGross`) immediately before the reconciliation check — satisfying the "client totals MUST be ignored / never trusted" rule above — the reconcile guard cannot fail in practice on a v1 create/update/confirm path. It is retained as **defense-in-depth**: it catches a future regression should the recompute ever be bypassed (e.g. a new code path that trusts a client total or mutates totals out of band). It is documented in the error table (§4) as a defensive code, not a routinely-reachable client outcome. The shipped tests assert this honestly — they verify the recompute produces reconciling totals and that the guard is present, not that a normal client request can trip it.

### 2.9 Immutability of confirmed/posted invoices (MUST — SDD-AUDIT-001)
- A `Confirmed`, `Posted`, `Cancelled`, or `Reversed` invoice's header, lines, totals, and `DocumentNumber` MUST NEVER be UPDATEd. The only permitted mutations are the state-flag transitions defined above (confirm→post link, post→reversed flag) with their `RowVersion`/status-history.
- `PUT` against a non-`Draft` invoice MUST be rejected with `INVOICE_POSTED_IMMUTABLE`.
- There is NO hard `DELETE` of a confirmed-or-later invoice; a `Draft` MAY be deleted (`DELETE /api/v1/invoices/{id}`, requires `finance.invoice:create`), writing an audit delete row. A draft has no `DocumentNumber`, so no gapless number is consumed.

### 2.10 List & get (MUST)
- `GET /api/v1/invoices` MUST accept a `FilterRequest` and return `PagedResult<InvoiceDto>` (SDD-INFRA-005), default-ordered by `IssueDate` descending then `Id` (PK appended as the final deterministic term). `PageSize` capped at 200. Requires `finance.invoice:read`.
  - Filterable/sortable surface MUST be opt-in via `[Filterable]`/`[Sortable]` on `Invoice`: `DocumentNumber`, `DocumentType`, `Direction`, `Status`, `CounterpartyId` (filter only), `CurrencyCode`, `IssueDate`, `DueDate`, `CreatedAt`, plus the two settlement columns `SettledAmount` and `SettlementStatus` that §2.14 requires. `CreatedAt` is enumerated here because the shipped aggregate carries the attributes on it (`Invoice.cs:140-142`) and "newest first" is a useful operator default; the spec is widened to the shipped surface rather than the attributes stripped. Every other property — including `ExchangeRate`, `LastSettlementAppliedAt`, `JournalEntryId`, `CorrectsInvoiceId` and the Warehouse source-document pair — MUST stay off the surface.
  - The list MUST NOT be cached (invoices are transactional data — SDD-INFRA-004 forbids caching them).
- `GET /api/v1/invoices/{id}` MUST return the invoice with its lines, or `INVOICE_NOT_FOUND` (404). Requires `finance.invoice:read`. MUST NOT be cached.

### 2.11 Domain events (MUST — SDD-INFRA-006)
- Events MUST be `sealed record` types implementing `IFinanceEvent` in `Finance.ServiceModel/Events/Invoices/`, with `required` properties + `MessageId` + `CorrelationId` + `OccurredAt`, published via the transactional outbox only.
- `InvoiceConfirmedEvent` MUST carry: `MessageId`, `CorrelationId`, `OccurredAt`, `InvoiceId`, `DocumentNumber`, `DocumentType`, `Direction`, `CounterpartyId`, `CurrencyCode`, `BaseCurrencyCode`, `IssueDate`, `PostingRuleKey`, `NetTotal`, `TaxTotal`, `GrossTotal`.
  - **(SDD-PAY-002 settlement amendment — shipped in Batch 17.)** `InvoiceConfirmedEvent` MUST additionally carry `DueDate` (`DateTimeOffset`, sourced from `Invoice.DueDate`) and `BookingExchangeRate` (`decimal` / `DECIMAL(18,6)` semantics, sourced from the frozen `Invoice.ExchangeRate` column, §2.14 — and NEVER hard-coded to `1.000000`). Both are additive (§5). They are declared **nullable** (`DateTimeOffset?` / `decimal?`) rather than `required` — a deliberate wire-compatibility decision, not an oversight: a `required` non-nullable member would fail to deserialize an `InvoiceConfirmedEvent` already sitting in a transactional-outbox row or a `<queue>_error` DLQ entry from before this amendment, which a rolling deploy makes a routine occurrence. The publisher obligation is therefore enforced by SPEC and by test rather than by the compiler: `InvoiceService` MUST always populate both, and `Confirm_PublishesInvoiceConfirmedEvent_CarryingDueDateAndBookingExchangeRate` plus `Confirm_NonBaseCurrencyInvoice_PublishesItsRealBookingExchangeRate_NotOne` (§6.7) pin it. Consumers MUST treat a null as a pre-amendment message and apply SDD-PAY-002 §2.2's fallback. Once every environment has drained its pre-amendment outbox and DLQ backlog, a follow-up `CHG-*` MAY tighten both to `required` and delete the fallback. The obligation, its rationale and SDD-PAY-002's degraded fallback are stated in full in §2.15; this bullet list is the authoritative payload, so the two fields are grown IN PLACE here. Both now ship on the record (`src/Finance.ServiceModel/Events/Invoices/InvoiceConfirmedEvent.cs` — `DueDate` and `BookingExchangeRate`, both nullable as specified), so SDD-PAY-002 §2.2's degraded fallback (`DueDate := IssueDate` + `BookingExchangeRate := 1.000000`) is no longer taken for any event this service publishes.
- `InvoiceCancelledEvent` MUST carry: `MessageId`, `CorrelationId`, `OccurredAt`, `InvoiceId`, `DocumentNumber`, `Reason`.
- **(SDD-PAY-002 settlement amendment — shipped in Batch 17.)** `InvoiceReversedEvent` (`src/Finance.ServiceModel/Events/Invoices/InvoiceReversedEvent.cs`, published by the Invoice service from the §2.7 reversal path) MUST carry: `MessageId`, `CorrelationId`, `OccurredAt`, `InvoiceId` (the reversed ORIGINAL), `DocumentNumber`, `CorrectingInvoiceId` (the Credit/Debit Note whose full offset reversed it — the other end of the note's shipped `CorrectsInvoiceId` link, §2.7), and `Reason`. It MUST be a `sealed record` implementing `IFinanceEvent` with `required` init-only properties, in the same folder and the same shape as the three shipped invoice events. Unlike `InvoiceCancelledEvent.DocumentNumber` (nullable — a draft cancel has no number), `DocumentNumber` here MUST be `required` and non-nullable: `Reversed` is reachable ONLY from `Posted` (§2.1) and every `Posted` invoice was numbered at confirm (§2.4).
- `InvoicePostedEvent` (the dedicated back-event published by the **Journal** service through ITS outbox once it posts the JE, §2.5) MUST carry: `MessageId`, `CorrelationId`, `OccurredAt`, `InvoiceId`, `JournalEntryId`, `JournalEntryNumber`. It lives in `Finance.ServiceModel/Events/Invoices/` alongside the invoice-published events because it is part of the invoice posting contract, even though the Journal service is its publisher.
- `InvoiceConfirmedEvent`, `InvoiceCancelledEvent`, and `InvoiceReversedEvent` MUST be published by the Invoice service via the EF Core transactional outbox configured on `InvoicesDbContext`, atomic with the DB transaction; `InvoicePostedEvent` is published by the Journal service via its own outbox. The publishers MUST NOT publish outside the outbox and MUST NOT wrap the publish in try/catch.

### 2.13 Edge cases (MUST)
- **Confirm with no lines.** `POST .../confirm` on a draft with zero lines MUST return `INVOICE_LINES_REQUIRED` before any number is allocated.
- **Confirm with mismatched totals.** A draft where `Σ LineGross ≠ Σ LineNet + Σ LineTax`, or header totals diverge from the line sums, MUST return `INVOICE_TOTALS_MISMATCH` before any number is allocated. (Per the §2.8 note, this is a defensive fail-fast invariant: the service recomputes header totals from the lines before the check, so it is unreachable through the normal v1 paths and is retained as defense-in-depth.)
- **Re-confirming a confirmed invoice.** `POST .../confirm` on a `Confirmed`/`Posted` invoice MUST return `INVOICE_NOT_DRAFT` — never a second gapless number, never a duplicate `InvoiceConfirmedEvent`.
- **Confirm into a closed period (post-FIN-004).** MUST return `INVOICE_PERIOD_CLOSED`; with the default always-open guard this path is unreachable but the code and test stub MUST exist.
- **Editing/deleting a confirmed-or-later invoice.** `PUT`/`DELETE` on a `Confirmed`/`Posted`/`Cancelled`/`Reversed` invoice MUST return `INVOICE_POSTED_IMMUTABLE`.
- **Cancelling a posted invoice.** MUST return `INVALID_INVOICE_STATE_TRANSITION` (correct via a Credit/Debit Note instead).
- **Duplicate posting back-event (replay).** A redundant `InvoicePostedEvent` for an already-`Posted` invoice MUST be a no-op (idempotency, SDD-INFRA-006) — never a duplicate `JournalEntryId`, never a second `Posted` transition.
- **Concurrent confirm of the same draft.** Two simultaneous confirms — one MUST win; the other MUST fail with `CONCURRENT_MODIFICATION` (RowVersion mismatch).
- **System-created draft from a duplicate Warehouse event.** Handled by SDD-INT-WH-001 (idempotency + source-document dedupe); this spec's create path MUST be safe to call once per source document.
- **Cancelling an invoice that has settlements.** (SDD-PAY-002 amendment, §2.6/§2.14.) A `Draft`/`Confirmed` invoice with `SettledAmount > 0.00` MUST return `INVOICE_HAS_SETTLEMENTS` and write nothing — deallocate in the Payments service first.
- **Cancel racing an in-flight allocation.** (SDD-PAY-002 amendment, §2.6.) Because `SettledAmount` is an asynchronously-fed mirror, a cancel whose allocation event has not yet been applied here MUST be expected to PASS the best-effort guard and succeed, leaving an orphaned allocation row in `finance_payments`. This spec MUST NOT model it as an invoice-side failure: SDD-PAY-002's `InvoiceCancelledEvent` consumer is the authority that detects the orphan and logs the structured warning (SDD-PAY-002 §2.3/§2.14). When that orphan is later REPAIRED by an explicit deallocation in the Payments service, the resulting `PaymentDeallocatedEvent` carries `InvoiceSettledAmount = 0.00` and MUST be APPLIED to the already-`Cancelled` invoice per §2.15 — zeroing `SettledAmount`, re-deriving `SettlementStatus = Unsettled`, and leaving `Status = Cancelled` untouched. That is the §2.14 rule at work: the cancel PATH never writes the settlement columns, but a LATER allocation event does.
- **Replayed allocation event.** (SDD-PAY-002 amendment, §2.15.) A duplicate `PaymentAllocatedEvent`/`PaymentDeallocatedEvent` MUST be a no-op — `SettledAmount` MUST NEVER be double-counted. Guaranteed twice over: `IdempotencyFilter<T>` (Redis `SETNX` on `MessageId`) and absolute-value recomputation rather than delta application.
- **Out-of-order allocation events for the same invoice.** (SDD-PAY-002 amendment, §2.14/§2.15.) Two allocation events for the SAME invoice can be APPLIED in the wrong order — the §2.15 `RowVersion` serialization supplies exactly that reordering when the first event loses the race and retries after the second has committed. The consumer MUST DROP any event whose `OccurredAt` is strictly older than the invoice's `LastSettlementAppliedAt` (silently and successfully — no write, no audit row, no dead letter) so the newer authoritative total survives; an event with an EQUAL `OccurredAt` MUST be applied. Without this the invoice would sit at the older figure permanently while `finance_payments` held the higher total, and no further event would ever correct it.
- **Full settlement of a posted invoice.** (SDD-PAY-002 amendment, §2.14.) `SettledAmount == GrossTotal` MUST derive `SettlementStatus = Settled` while `Status` REMAINS `Posted`; no lifecycle transition, no `invoice_status_history` row, no event. `Settled` is NOT a lifecycle state.
- **Settlement event that would breach the ceiling.** (SDD-PAY-002 amendment, §2.14.) An event that would drive `SettledAmount` above `GrossTotal` (or below `0.00`) MUST make the consumer THROW for retry/DLQ — never clamp, truncate, or silently persist the over-value. Unreachable through the sanctioned path (SDD-PAY-002 §2.5 forbids over-allocation); retained as defense-in-depth. The retry-then-dead-letter outcome depends on **CHG-FIX-006** — see the next edge case.
- **Settlement event for an unknown invoice id.** (SDD-PAY-002 amendment, §2.15.) MUST make the consumer throw so MassTransit retries then DLQs — MUST NOT be swallowed and MUST NOT create a placeholder invoice.
  - **Prerequisite: CHG-FIX-006 — the fix to the shared `IdempotencyFilter<T>`, shipped in Batch 17 (`src/Infrastructure/Messaging/Finance.Infrastructure.Messaging/Filters/IdempotencyFilter.cs:81-131`).** Every "throw → MassTransit retries (1s/5s/15s) → dead-letter" statement in §2.13 and §2.15 is true only because of it. Verified: `bus.UseMessageRetry(retry => retry.Intervals(RetryIntervals))` is registered BEFORE `bus.UseFinanceIdempotency(context)` (`src/Infrastructure/Messaging/Finance.Infrastructure.Messaging/MessagingServiceCollectionExtensions.cs:122-123`), so retry is the OUTER filter and `IdempotencyFilter<T>` the INNER one. Before CHG-FIX-006 the filter kept its Redis claim when the consumer threw, so the retry's re-entry was short-circuited as a duplicate of ITSELF, logged as "Duplicate message skipped", and acknowledged — nothing ever reached `<queue>_error`. CHG-FIX-006 releases the claim on a failed consume and rethrows with the stack intact, so the retry and dead-letter policy runs to completion. Without it these edge cases would be fiction, not defense-in-depth. One residual risk remains and is accepted: if Redis itself is unreachable at the moment the claim is released, the shipped filter logs an ERROR naming the still-held claim and returns — the ORIGINAL consumer exception still propagates, but that one message can be skipped as a duplicate for the rest of the TTL (CHG-FIX-006 §9).

### 2.14 Settlement state — `SettledAmount` + `SettlementStatus` + the frozen `ExchangeRate` + `LastSettlementAppliedAt` (MUST — SDD-PAY-002)

> **Numbering note.** §2.14/§2.15 are APPENDED after the §2.13 edge-case list instead of being inserted before it: §2.1–§2.13 are shipped sections already cited by `§`-reference from `Finance.Common/ErrorCodes/InvoiceErrorCodes.cs` and the Batch-16 test suite, so renumbering them would break those references. The settlement edge cases are added to §2.13 in place, and every obligation of the Batch-17 amendment that belongs to a shipped section is added there in place too: the `INVOICE_HAS_SETTLEMENTS` cancel guard (§2.6), the `InvoiceReversedEvent` publish (§2.7) and its payload/shape (§2.11), the two additive `InvoiceConfirmedEvent` fields (§2.11, stated in full in §2.15), and the Journal-side duplicate-post hardening (§2.5). Everything in §2.14/§2.15, plus every one of those in-place additions, is **shipped and tested** (Batch 17, 2026-08-05 — §6.7 records the covering tests and the two remaining unit-test gaps).

- The `Invoice` aggregate MUST grow exactly FOUR columns and no more:
  - `SettledAmount` (`DECIMAL(18,2)`, `NOT NULL`, default `0.00`) — how much of this invoice's `GrossTotal` payment allocations have applied, in the invoice's own `CurrencyCode`. `decimal` only, never `double`/`float` (SDD-FIN-005).
  - `SettlementStatus` — the DERIVED state, persisted as a string via `.HasConversion<string>()` + `.HasMaxLength(20)` (mirroring the existing `Status` column) so it is filterable/sortable without recomputation.
  - `ExchangeRate` (`DECIMAL(18,6)`, `NOT NULL`, default `1.000000`) — the invoice's **booking rate**: the rate at which its `CurrencyCode` amounts were booked into `BaseCurrencyCode`. It MUST be set at invoice creation from the transaction-date rate and then FROZEN for the life of the document, exactly as `BaseCurrencyCode` already is (§2.3) — `1.000000` when `CurrencyCode == BaseCurrencyCode`, and the caller-supplied rate for a non-base-currency invoice until SDD-FIN-005's automatic lookup lands (§1, excluded scope). `decimal` / `DECIMAL(18,6)`, never `double`/`float` (SDD-FIN-005). It is the ONLY source of `InvoiceConfirmedEvent.BookingExchangeRate` (§2.15): the shipped aggregate carries `CurrencyCode` and `BaseCurrencyCode` but NO rate column, so without this column the event could only ever carry a fabricated `1.000000` — which would corrupt SDD-PAY-002's `RealizedFxDifference` and SDD-PAY-003's `BaseOutstanding` for every non-base-currency invoice (a EUR invoice on a BGN base would be reported as if it were BGN). Unlike the other three new columns, `ExchangeRate` is part of the ISSUED document and IS covered by the §2.9 immutability rule — it MUST NEVER be written after confirm.
  - `LastSettlementAppliedAt` (`DATETIMEOFFSET`, `NULL`) — the **ordering token**: the `OccurredAt` of the most recent allocation event this invoice has APPLIED (§2.15). `NULL` means no settlement event has been applied yet, so the first event always applies. Like `SettledAmount` and `SettlementStatus` — and unlike `ExchangeRate` — it is settlement bookkeeping ABOUT the document, is written after posting, and is therefore covered by the §2.9 carve-out below rather than by the immutability rule.
- **Why the ordering token is REQUIRED, and what it actually guarantees.** Assigning the event's absolute `InvoiceSettledAmount` (§2.15) is idempotent for a REPLAY of the SAME message, but it is NOT commutative across DIFFERENT messages — and the `RowVersion` serialization in §2.15 is itself a reordering mechanism. Worked example: `GrossTotal = 1000.00`; payment A allocates `300.00` (its event carries `InvoiceSettledAmount = 300.00`), payment B then allocates `700.00` (its event carries `1000.00`). Both events consume concurrently, A loses the `RowVersion` race, retries, and assigns `300.00` LAST — the invoice then reads `SettledAmount = 300.00` / `PartiallySettled` PERMANENTLY while `finance_payments` holds `1000.00` in allocation rows, and no further event will ever correct it. The mirror is therefore NOT "idempotent by construction" and NOT self-convergent; the guarantee this spec makes is **last-writer-by-`OccurredAt` wins, and strictly older events are dropped**. That requires SDD-PAY-002 to stamp `OccurredAt` INSIDE the allocation transaction on both `PaymentAllocatedEvent` and `PaymentDeallocatedEvent` (SDD-PAY-002 §2.10 already declares the field on both, and `src/Finance.ServiceModel/Events/IFinanceEvent.cs` makes `OccurredAt` mandatory on every Finance event, so nothing new is added to the wire format — only the stamping point and this side's comparison are new).
- `SettlementStatus` MUST use the SHARED enum `SettlementStatus` (`src/Finance.Common/Enums/SettlementStatus.cs`, explicit values `Unsettled = 1`, `PartiallySettled = 2`, `Settled = 3`), which is DECLARED and OWNED by SDD-PAY-002 §2.8. There MUST be exactly ONE type, ONE file, and ONE set of values: this spec MUST NOT declare an invoice-specific `InvoiceSettlementStatus` fork. The property stays `Invoice.SettlementStatus` and simply references the shared type. Both sides live in `Finance.Common`, so a second type would be a silent contract fork across the service boundary (RESOLVED — §7).
- The value MUST be DERIVED from the two decimals by EXACT `DECIMAL(18,2)` comparison — never supplied by a caller, never persisted independently of `SettledAmount`, never transitioned through `IWorkflowEngine<Invoice>`:
  - `SettledAmount == 0.00` → `Unsettled`.
  - `0.00 < SettledAmount < GrossTotal` → `PartiallySettled`.
  - `SettledAmount ≥ GrossTotal` → `Settled` (the `>` branch is defensive only — see the invariant below).
- There MUST be no tolerance band and no residual write-off: `GrossTotal − 0.01` settled MUST be `PartiallySettled`, not `Settled`. This derivation MUST reproduce SDD-PAY-002 §2.8 exactly — the two are independent copies on either side of the service boundary and MUST NOT be allowed to diverge. On this side it MUST live in exactly ONE place and MUST NOT be duplicated in the AutoMapper profile, the DTO, or the consumers.
- **Invariant (defensive).** `SettledAmount` MUST NEVER exceed `GrossTotal` and MUST NEVER be negative. SDD-PAY-002 §2.5 forbids over-allocation at the source (`PAYMENT_ALLOCATION_EXCEEDS_OUTSTANDING`), so a breach is unreachable through the sanctioned path; the ceiling is retained as defense-in-depth against a lost, duplicated, or hand-published event, or a future regression. A breach MUST make the consumer FAIL (throw → MassTransit retry → DLQ, §2.15) rather than clamp, truncate, or silently write the over-value — a quietly clamped ledger figure is worse than a DLQ'd message.
- **Settlement is ORTHOGONAL to the lifecycle (§2.1).** `SettlementStatus` MUST NOT appear in any `AllowedNextStates` set, MUST NOT be registered as an `IWorkflowState<Invoice>`, and MUST NEVER drive a lifecycle transition. A fully-settled invoice REMAINS `Posted` — there is NO `Posted → Settled` transition and `Settled` is NOT a lifecycle state. Conversely the cancel PATH (§2.6) and the reverse PATH (§2.7) MUST THEMSELVES never write `SettledAmount`, `SettlementStatus`, or `LastSettlementAppliedAt`: a terminal transition carries forward exactly the settlement figures the invoice held at that moment and rewrites no history (SDD-AUDIT-001). That is a rule about the TRANSITION, not a freeze on the columns — what a LATER allocation event does to an already-terminal invoice is governed SOLELY by §2.15, which APPLIES it whatever the lifecycle state, `Cancelled`/`Reversed` included. The distinction is load-bearing rather than pedantic: the orphan-repair path both §2.6 and SDD-PAY-002 §2.3/§7 designate is a deallocation issued AFTER a cancel has won the race against an in-flight allocation, and its event carries `InvoiceSettledAmount = 0.00`; §2.15 MUST apply it, so the mirror stops claiming cash the Payments service has released and the derived status falls back to `Unsettled` while `Status` stays `Cancelled`. A terminal invoice therefore keeps its settlement figures until — and only until — a later allocation event says otherwise (§2.13 edge case "Cancel racing an in-flight allocation"; §6.7 `AllocationConsumer_DeallocationAfterCancel_ZeroesSettledAmount_AndRederivesStatus`). The two axes MUST be read independently: `Status` = the issuance/posting lifecycle (§2.1); `SettlementStatus` = how much cash has been matched against the document.
- Maintaining these three columns (`SettledAmount`, `SettlementStatus`, `LastSettlementAppliedAt`) MUST NOT invoke `IWorkflowEngine<Invoice>`, MUST NOT append an `invoice_status_history` row, and MUST NOT touch `DocumentNumber`, lines, or totals — so it is NOT blocked by the §2.9 immutability rule. That rule protects the ISSUED document (header, lines, totals, number); `SettledAmount`/`SettlementStatus`/`LastSettlementAppliedAt` are settlement bookkeeping ABOUT the document, not part of it. This exception MUST stay explicit and narrow: together with the §2.5 `JournalEntryId`/`PostedAt` link and the §2.7 `Reversed` flag, these are the ONLY columns a posted invoice may have written after posting. The third new column, `ExchangeRate`, is NOT in that set — it is frozen at creation and belongs to the issued document, so §2.9 protects it like the totals and the number.
- Both OPERATOR-FACING settlement columns (`SettledAmount`, `SettlementStatus`) MUST be exposed on `InvoiceDto` (additive response fields, §5) and MUST NOT be cached — settlement state is transactional data (SDD-INFRA-004, §2.10). `ExchangeRate` MAY be exposed on `InvoiceDto` for FX display; this amendment does not require it. `LastSettlementAppliedAt` is INTERNAL consumer bookkeeping: it MUST NOT be required on `InvoiceDto` and MUST NOT enter the `[Filterable]`/`[Sortable]` surface — it answers "which event won", which is a diagnostic question, not an operator query.
- `SettledAmount` and `SettlementStatus` MUST opt in via `[Filterable]`/`[Sortable]` (SDD-INFRA-005) so "unsettled invoices" is a server-side filter, not a client-side scan.
- **Migration (MUST — persona-database).** All FOUR columns MUST arrive in ONE NEW additive migration — shipped as `src/Databases/Finance.Invoices.DBModel/Migrations/20260805182742_AddInvoiceSettlement.cs`; `ExchangeRate` and `LastSettlementAppliedAt` ride in the SAME migration as the two settlement columns, not separate ones. The already-applied `20260609214356_InitialCreate` MUST NEVER be edited (it was not). The migration MUST backfill every existing row with `SettledAmount = 0.00`, `SettlementStatus = 'Unsettled'`, `ExchangeRate = 1.000000` (every pre-existing invoice was booked in a base-currency context, §1), and `LastSettlementAppliedAt = NULL` (no settlement event has been applied to any pre-existing invoice, so the first one to arrive must win) — the shipped migration achieves the backfill through the `NOT NULL` + `defaultValue` on each added column — and SHOULD add `IX_Invoices_SettlementStatus` for the settlement read patterns (it does; pinned by `InvoiceConfiguration_IndexesSettlementStatus_ForTheSettlementReadPatterns`, §6.7). `LastSettlementAppliedAt` MUST be configured as a plain nullable `datetimeoffset` with NO `SYSDATETIMEOFFSET()` default — the value is the EVENT's `OccurredAt`, never the row's write time (contrast `CreatedAt`, which does carry the default in the shipped `InvoiceConfiguration`).

### 2.15 Allocation-event consumers — the inbound settlement handshake (MUST — SDD-PAY-002 / SDD-INFRA-006)

- `Finance.Invoices.API` MUST consume SDD-PAY-002's two outbox events — `PaymentAllocatedEvent` and `PaymentDeallocatedEvent` — from consumers in `src/Interfaces/Invoices/Finance.Invoices.API/Consumers/`, registered inside the existing `AddFinanceMessageBus<InvoicesDbContext>(configuration, ConfigureConsumers)` delegate alongside `InvoicePostedEventConsumer`.
- The handshake is **one-way** (SDD-PAY-002 §2.10): this service MUST NOT publish a back-event in response to an allocation event, MUST NOT call the Payments service, and MUST NOT be waited on by allocation. (The `InvoiceReversedEvent` of §2.7/§2.11 is not a counter-example: it is a lifecycle publish on the reversal path that SDD-PAY-002 happens to consume, never a reply to an allocation event.) A settlement update that has not arrived yet is projection lag, NOT a failure — the Payments-local projection is the authority for the allocation invariants, and this mirror is for invoice-side display and the §2.6 cancel guard.
- Each consumer MUST be wrapped by `IdempotencyFilter<T>` — Redis `SETNX finance:processed:{MessageId}`, 7-day TTL (SDD-INFRA-006). Neither consumer MUST hand-roll dedupe logic.
  - **Prerequisite: CHG-FIX-006 (shipped in Batch 17).** Every throw-for-recovery rule in this section — the unknown-`InvoiceId` throw (step 1), the ceiling breach (step 3), and the §2.13 edge cases — assumes that a consumer exception produces MassTransit retries (1s/5s/15s, `RetryIntervals` in `MessagingServiceCollectionExtensions.cs`) and then a dead letter. Until CHG-FIX-006 the shipped filter did NOT release its Redis claim when the downstream pipe threw, and because retry is registered as the OUTER filter and idempotency the INNER one (`MessagingServiceCollectionExtensions.cs:122-123`), the retry's re-entry matched the filter's OWN claimed key, was logged as a duplicate, and was acknowledged — the message never reached `<queue>_error`. The fix releases the claim on a failed consume and rethrows, which is what makes these recovery contracts real. These consumers MUST NOT compensate for it themselves (no try/catch around the throw paths, no hand-rolled claim release).
- Beyond `MessageId` dedupe each consumer MUST assign ABSOLUTELY, because a post-TTL replay or a DLQ redelivery MUST NOT double-count cash: `SettledAmount` MUST be RECOMPUTED by ASSIGNING the authoritative value carried on the event (`InvoiceSettledAmount`, SDD-PAY-002 §2.10), NOT by incrementing or decrementing with the event's delta. A `+=`/`-=` double-counts on redelivery; an absolute assignment does not.
- **Absolute assignment alone is NOT sufficient — each consumer MUST also be ORDERED (§2.14).** Absolute assignment makes a REPLAY of the same message harmless, but it is not commutative across DIFFERENT messages, so two allocation events applied in the wrong order leave the mirror permanently wrong (the §2.14 worked example). The consumers MUST therefore compare the event's `OccurredAt` against the stored `LastSettlementAppliedAt`:
  - `OccurredAt` **strictly older** than `LastSettlementAppliedAt` → the event is STALE and MUST be SKIPPED silently and successfully: no column write, no audit row, no throw, no dead letter. The message is acknowledged; a structured debug/information log (SDD-OBS-001) SHOULD record the drop with both timestamps.
  - `OccurredAt` **equal to** `LastSettlementAppliedAt` → MUST be APPLIED. Absolute assignment makes re-applying an equal-timestamped event harmless, and skipping on equality would drop a genuine second event that shares a timestamp.
  - `OccurredAt` **newer**, or `LastSettlementAppliedAt` **`NULL`** → MUST be APPLIED.
  - The guarantee this yields MUST be stated as it is — **last-writer-by-`OccurredAt` wins and strictly older events are dropped** — and MUST NOT be described as "idempotent by construction" or "convergent": a dropped stale event is not replayed later, and the mirror does not repair itself.
- On each DELIVERED event the service MUST, within a single transaction and in this order (steps 3–7 run only for an APPLIED event):
  1. Load the invoice tracked by the event's `InvoiceId`; an unknown id MUST make the consumer throw so MassTransit retries then DLQs (SDD-INFRA-006) — never swallowed, never a placeholder invoice.
  2. Evaluate the ordering token above against the loaded invoice's `LastSettlementAppliedAt`; a STALE event MUST return here as a successful no-op, before the ceiling assertion, the column writes, and the audit row.
  3. Assert the §2.14 ceiling against the invoice's own `GrossTotal`; a breach MUST throw (never clamp).
  4. Set `SettledAmount` to the event's `InvoiceSettledAmount` and recompute `SettlementStatus` LOCALLY via the §2.14 derivation. The event also carries a property named `InvoiceSettlementStatus` (a value of the shared `SettlementStatus` enum, SDD-PAY-002 §2.8/§2.10 — the property name is scoped to the event, not a second type); the local recomputation is authoritative for this database and MUST agree with it — a disagreement MUST be logged as a structured warning (SDD-OBS-001) and MUST NOT be resolved by trusting the remote value.
  5. Stamp `LastSettlementAppliedAt` with the event's `OccurredAt` — on EVERY applied event, including one that leaves `SettledAmount` unchanged. Never `DateTimeOffset.UtcNow`, never the row's write time: the token must be comparable against the next event's `OccurredAt`.
  6. Write an audit `Update` row (`EventType = "InvoiceSettlementUpdated"`, `BeforeJson` = the pre-change settlement snapshot, `AfterJson` = the post-change snapshot — both MUST include `LastSettlementAppliedAt`, so the audit trail shows which event won) BEFORE any other side effect (audit-first, SDD-AUDIT-001). Settlement is not on SDD-AUDIT-001's sensitive-operation list, so no `Reason` is REQUIRED.
  7. `SaveChangesAsync` and commit — the invoice `RowVersion` increments. That increment SERIALIZES two allocation events landing on the SAME invoice concurrently; it does NOT order them, which is precisely why the ordering token is required (the loser's retry would otherwise re-apply an older absolute value last, §2.14).
- The consumers MUST NOT invoke `IWorkflowEngine<Invoice>`, MUST NOT append an `invoice_status_history` row (no transition occurs — §2.14), MUST NOT publish any event, and MUST NOT create, mutate, or reverse a journal entry (settlement is sub-ledger matching, not posting — SDD-PAY-002 §1).
- An event MUST be applied whatever the invoice's lifecycle state, INCLUDING `Cancelled`/`Reversed`: SDD-PAY-002 §2.3 deliberately keeps allocation rows intact when an invoice is cancelled, so this mirror MUST stay faithful to those rows rather than reject the update. This is the section §2.14 defers to, and there is NO contradiction between them: §2.14 forbids the cancel/reverse PATHS from writing the settlement columns, while this section governs what LATER events do to an already-terminal invoice. The load-bearing case is the orphan-repair deallocation of §2.6 — it carries `InvoiceSettledAmount = 0.00`, MUST be applied to a `Cancelled` invoice, MUST zero `SettledAmount` and re-derive `SettlementStatus = Unsettled`, and MUST leave `Status`, `DocumentNumber`, lines and totals untouched. Rejecting or skipping it would leave the invoice permanently claiming cash that `finance_payments` no longer holds.
- `CorrelationId` MUST be taken from the event for the ambient logging scope and the audit row, so a settlement update is traceable back to the originating allocation (SDD-INFRA-001 / SDD-OBS-001).
- **Two additive `InvoiceConfirmedEvent` fields (MUST — SDD-PAY-002 §2.2).** SDD-PAY-002's `InvoiceOpenItem` projection needs the invoice's due date and its booking exchange rate, neither of which the shipped event (§2.11) carries. Both MUST be added to `InvoiceConfirmedEvent` as additive, non-breaking fields: `DueDate` (`DATETIMEOFFSET`), sourced from `Invoice.DueDate`, and `BookingExchangeRate` (`DECIMAL(18,6)`), which MUST be sourced from the new frozen `Invoice.ExchangeRate` column (§2.14) and MUST NOT be hard-coded to `1.000000` — a fabricated rate would corrupt SDD-PAY-002's `RealizedFxDifference` and SDD-PAY-003's `BaseOutstanding` for every non-base-currency invoice. Adding an event field is additive (§5). Until they land SDD-PAY-002 MUST use its documented fallback (`DueDate := IssueDate`, `BookingExchangeRate := 1.000000`), which understates due dates for SDD-PAY-003 aging and flattens base-currency reporting — the fallback is a contingency if this amendment slips, never the design.

Verified cause of the defect: the pre-Batch-17 consumer posted unconditionally and `JournalEntry` carried no source-document reference (only `ReversesEntryId`), so a redelivery after `IdempotencyFilter<T>`'s 7-day `MessageId` TTL, or a `finance-journal_error` replay, posted a SECOND balanced entry and silently overstated the control account. The two `JournalEntry` columns, the Journal migration `20260805174405_AddJournalEntrySourceDocument` and the unique filtered index that backstops them are owned by SDD-PAY-001 §2.5, which applies the identical guard to `("Payment", PaymentId)`; this spec records only the invoice-side obligation and its tests (§6.7). Purely additive: no posting rule, no event payload, no invoice-side column and no handshake step changed — an at-least-once side effect became exactly-once.
  - The two allocation consumers' throw-for-retry recovery contract — and every "throw → retry → dead-letter" statement in §2.13/§2.15 — depends on **CHG-FIX-006**, the Batch-17 fix to the shared `IdempotencyFilter<T>` that releases the Redis claim when a consume fails so MassTransit's retry and dead-letter policy can run at all (§2.15).
  Nothing in the `Draft → Confirmed → Posted` lifecycle changes: settlement is ORTHOGONAL to it (§2.14), the `InvoiceReversedEvent` publish adds no state and no transition, and the §2.5 duplicate-post hardening adds no state, no transition and no new event. Changing the settlement DERIVATION (introducing a tolerance band or a write-off rule) WOULD be breaking, would require `/api/v2/` + a `CHG-ENH-*`, and MUST be changed on BOTH sides of the boundary in the same change (SDD-PAY-002 §2.8). Removing the ordering token — reverting to unordered absolute assignment — MUST NOT be treated as a simplification: it reintroduces the permanent-divergence defect documented in §2.14 and would require the same joint change.
- **Deferred (future versions / specs):**
  - **Automatic `Posted → Reversed` DETECTION on a fully-offsetting Credit Note (§2.7).** The workflow keeps `Posted → { Reversed }` legal, the `CorrectsInvoiceId` linkage between a note and its original IS implemented and tested, and Batch 17 shipped the transition PATH itself — `IInvoiceService.MarkReversedAsync` (flag + status history + audit `InvoiceReversed` + outbox `InvoiceReversedEvent`, `InvoiceAuditEventTypes.InvoiceReversed`). What remains DEFERRED is the automatic full-offset *detection* that decides a note fully offsets its original and calls that path, and any HTTP surface for it: `InvoicesController` exposes no reverse endpoint (verified — only `confirm`/`post`/`cancel`), so in v1 nothing invokes `MarkReversedAsync` in production and a posted original stays `Posted` after a note is issued. The shipped §6.5 tests assert that shipped behaviour (the original stays `Posted`), not the deferred auto-reverse. This deferral no longer depends on the CREDIT_NOTE / DEBIT_NOTE posting-rule templates — those now ship (§7) — only on the detection rule and its trigger being specified.
  - **Payment allocation itself, AP/AR aging, and counterparty balances** — SDD-PAY-002 / SDD-PAY-003 (additive; no change to this lifecycle). The invoice-side settlement MIRROR is NO LONGER deferred — it is specified in §2.14/§2.15 by the 2026-08-05 growth-log entry above and shipped in Batch 17.
  - **VAT journals / НАП export** — SDD-RPT-003 / SDD-INT-NAP-001 (read the posted invoices; no change here).
  - **Optimistic synchronous posting** at confirm — a future `CHG-ENH-*` (§2.5) if required; the event-driven path is v1.
  - **FX rate resolution** — SDD-FIN-005. The invoice now CARRIES its booking rate in the frozen `ExchangeRate` column (§2.14, added by the settlement amendment), so downstream FX arithmetic has a real source; what stays deferred is the automatic RESOLUTION of that rate from a rate table (v1 takes it from the create request, `1.000000` in a base-currency context).
  - **Approval state** between `Draft` and `Confirmed` — a future `CHG-FEAT-*` (new state + `AllowedNextStates` + migration per SDD-INFRA-008 §5).
- Adding an event field is additive; changing the state set/transition semantics or a sequence format pattern is breaking and requires `/api/v2/` + a `CHG-ENH-*` (+ an enum migration / НАП-stability review for number formats).

## 7. Resolved Decisions & Open Items

### Resolved
- **One aggregate, four document types.** `Invoice` discriminated by `DocumentType` (`PurchaseInvoice`/`SaleInvoice`/`CreditNote`/`DebitNote`) + `Direction` (`AP`/`AR`); header `invoices` + child `invoice_lines`. `invoices.id` = `UNIQUEIDENTIFIER`/`NEWSEQUENTIALID()` (exposed via events), `correlation_id` column, `DECIMAL(18,2)` amounts / `DECIMAL(18,6)` rates, `DATETIMEOFFSET` timestamps, outbox tables in the same DB (Plan Appendix A).
- **State set.** `Draft → Confirmed → Posted`; `Cancelled` from `Draft`/`Confirmed`; `Posted → Reversed` via a fully-offsetting Credit Note. `Cancelled`/`Reversed` terminal. Via `IWorkflowEngine<Invoice>` (SDD-INFRA-008).
- **Numbering at confirm.** Gapless `PINV`/`SINV`/`CN`/`DN` number via `ISequenceGenerator`, formatted by `ICountryStrategy.GenerateDocumentNumber`. Draft has NULL `DocumentNumber`; a cancelled confirmed invoice keeps (never recycles) its number.
- **Posting handshake (chosen): event-driven with a dedicated back-event.** Confirm publishes `InvoiceConfirmedEvent` via the outbox; the Journal service consumes it, posts the JE (SDD-FIN-006), and publishes back the dedicated `InvoicePostedEvent` (NOT the generic `JournalEntryPostedEvent`, which is multi-purpose and already consumed by EventLog); the Invoice service's idempotent consumer links `JournalEntryId` and moves `Confirmed → Posted`. The Invoice service never posts a JE itself. Optimistic synchronous posting is the documented, deferred alternative (§2.5).
- **Tax via the country strategy.** Line/document totals + rounding via `ICountryStrategy`; core stays country-agnostic; `decimal` only.
- **Corrections via notes.** Posted invoices are immutable; corrected only by Credit/Debit Notes linked via `CorrectsInvoiceId` — mirroring SDD-FIN-002 reversal.
- **No caching.** Invoices are transactional data (SDD-INFRA-004).

### Resolved by the Pass-A implementator (Batch 16)
- **Back-event type — RESOLVED: dedicated `InvoicePostedEvent`.** The Journal service publishes a dedicated `InvoicePostedEvent` (`InvoiceId`, `JournalEntryId`, `JournalEntryNumber`) through its outbox after posting, NOT the generic `JournalEntryPostedEvent`. The generic event is published for every journal entry and is already consumed by EventLog; a dedicated event keeps the invoice→posting correlation explicit and avoids fragile multi-purpose routing/matching. The event record lives in `Finance.ServiceModel/Events/Invoices/` (it is part of the invoice posting contract) even though the Journal service publishes it.
- **Period-open guard source — RESOLVED for v1: default always-open.** The Invoice service registers `IInvoicePeriodGuard` → `AlwaysOpenInvoicePeriodGuard` (mirroring the Journal `AlwaysOpenPostingPeriodGuard` seam), run as an `IChainValidator<WorkflowContext<Invoice>>` on the `Draft → Confirmed` transition. When SDD-FIN-004's lookup is reachable from this service, a gateway-backed guard replaces only that DI registration and returns `INVOICE_PERIOD_CLOSED`.
- **`post` endpoint vs back-event — RESOLVED: endpoint exposed in v1.** `POST /{id}/post` is exposed as the manual-completion/visibility seam (`finance.invoice:post`); the asynchronous `InvoicePostedEvent` consumer is the primary path. If the JE is already linked the endpoint confirms `Posted`; otherwise it returns `INVOICE_NOT_CONFIRMED` (posting-pending).
- **`PostingRuleKey` mapping — RESOLVED.** `InvoiceDocumentTypeMap` in the Invoice service maps `SaleInvoice → SALE_INVOICE`, `PurchaseInvoice → PURCHASE_INVOICE`, `CreditNote → CREDIT_NOTE`, `DebitNote → DEBIT_NOTE`; the key is carried on `InvoiceConfirmedEvent`. All four keys now have a seeded BG template: Batch 16 shipped `SALE_INVOICE` and `PURCHASE_INVOICE`, and Batch 17 added `CREDIT_NOTE` and `DEBIT_NOTE` with the sides SDD-PAY-001 §2.13 specifies — a credit note takes the OPPOSITE side to a sale invoice on every selector (credit `411` gross, debit `701` net, debit `4532` tax) and a debit note REPEATS the sale-invoice sides (`BulgariaStrategy.cs:150-174`; `BuildDefaultRules()` now returns SEVEN templates, `:101-110`). Four side-asserting tests pin them (`BulgariaStrategy_SeedsCreditNoteRule_WithSidesMirroringSaleInvoice`, `BulgariaStrategy_CreditNoteRule_TakesOppositeSideToSaleInvoice_ForEveryAccountSelector`, `BulgariaStrategy_SeedsDebitNoteRule_WithSidesRepeatingSaleInvoice`, `BulgariaStrategy_DebitNoteRule_RepeatsEverySaleInvoiceLine_SelectorSideAndAmountSource` — SDD-CTRY-001, SDD-FIN-006). Seeding into a live posting-rule store remains gated by the `EnablePostingRuleSeeding` feature flag (default `false` in the Journal template config, checked at `Finance.Journal.API/Program.cs:212`) plus accountant sign-off — the templates existing in code is NOT the same as note posting being enabled in an environment.
- **`ICountryStrategy` tax/number members shape — RESOLVED.** Grown with `decimal ApplyTaxRounding(decimal amount)`, `bool IsValidTaxRate(decimal rate)`, and `string GenerateDocumentNumber(InvoiceDocumentType documentType, long sequenceValue)`; `BulgariaStrategy` implements them (BGN, recognized rates 20% / 9% / 0%, `MidpointRounding.AwayFromZero` to 2 dp, BG prefixes ФПок/ФПр/КИ/ДИ). A new additive `ISequenceGenerator.NextValueAsync` returns the raw gapless counter so the country owns the number format.

### Resolved by the 2026-08-05 Phase-5 (Payments) amendment — SDD-PAY-002 settlement plus the SDD-PAY-001 duplicate-post hardening (Batch 17, shipped + tested)
- **In-place amendment, not a separate `CHG-*`.** The settlement columns extend an aggregate this spec already owns, so the behavior is recorded HERE with a dated §5 growth-log entry — the Batch-16 precedent (SDD-CTRY-001 / SDD-INFRA-003 / SDD-INFRA-006). A parallel `CHG-*` would split one aggregate's contract across two documents and guarantee drift.
- **Settlement lives ON the invoice, mirrored from events — never read across the boundary.** The invoice keeps its OWN `SettledAmount`; it MUST NOT be obtained by a synchronous read of the Payments service and MUST NOT be joined from `finance_payments` (Plan §8). SDD-PAY-002's `InvoiceOpenItem.SettledAmount` and this column are deliberately INDEPENDENT copies maintained from the same events, exactly as SDD-PAY-002 §2.2 states.
- **Settlement is orthogonal to the lifecycle.** No new lifecycle state, no new `AllowedNextStates` edge, no `invoice_status_history` row, no workflow engine call. A `Settled` invoice stays `Posted`. This is what keeps the amendment additive and the shipped §2.1 state machine untouched.
- **Absolute recomputation PLUS an ordering token — RESOLVED; the absolute assignment alone was NOT enough.** `SettledAmount` is assigned from the event's `InvoiceSettledAmount`, which on top of the `MessageId` `SETNX` filter is what survives a post-TTL replay without double-counting cash — but it is NOT commutative across DIFFERENT messages, and §2.15's own `RowVersion` serialization supplies exactly the reordering that breaks it: the loser of a `RowVersion` race retries and assigns its OLDER absolute value last, freezing the invoice at the lower figure forever while `finance_payments` holds the higher total (the §2.14 worked example). The mirror therefore also keeps `LastSettlementAppliedAt` and DROPS any event strictly older than it, applying equal timestamps. The honest guarantee is **last-writer-by-`OccurredAt`**; the earlier "idempotent by construction / convergent" phrasing overstated it and has been removed from §2.15. Alternatives rejected: a monotonic per-invoice sequence owned by SDD-PAY-002 (more cross-service coupling for the same outcome, since `OccurredAt` is already mandatory on every `IFinanceEvent`) and a synchronous re-read of the Payments service (Plan §8 forbids it).
- **Over-settlement throws; it never clamps.** The `SettledAmount ≤ GrossTotal` ceiling is defensive (SDD-PAY-002 §2.5 forbids over-allocation at the source). A breach DLQs the message rather than persisting a clamped figure — mirroring the §2.8 `INVOICE_TOTALS_MISMATCH` defense-in-depth stance and SDD-PAY-002 §2.8's unreachable `>` branch.
- **Cancel is blocked by settlements (best-effort — see the next bullet); posted invoices are unaffected.** `INVOICE_HAS_SETTLEMENTS` (409) guards only `Draft`/`Confirmed` cancellation — a `Posted` invoice was already uncancellable (§2.6) and is corrected by a Credit/Debit Note regardless of settlement.
- **The cancel guard is BEST-EFFORT, and SDD-PAY-002 is the authority — RESOLVED (not an open risk).** `SettledAmount` is an asynchronously-fed mirror and the handshake is one-way with no synchronous cross-service read (§2.15, SDD-PAY-002 §2.10), so a cancel racing an in-flight allocation CAN still orphan an allocation row. That is accepted, not hidden: the invoice side keeps the cheap guard for the ordinary operator mistake, and SDD-PAY-002's `InvoiceCancelledEvent` consumer performs the authoritative detection (existing `PaymentAllocation` rows on a cancelled invoice → structured NLog warning for the deferred reconciliation job, SDD-PAY-002 §2.3/§2.14/§7). Closing the race would require a synchronous read across the database-per-service boundary (Plan §8) and was rejected.
- **A terminal invoice's settlement columns — RESOLVED: the cancel/reverse PATH never writes them, LATER events still do.** §2.14 and §2.15 read as contradictory MUSTs until this round (§2.14 said a `Cancelled`/`Reversed` invoice "keeps whatever `SettledAmount` it had"; §2.15 says an event "MUST be applied whatever the invoice's lifecycle state, INCLUDING `Cancelled`/`Reversed`"), and they collided on precisely the orphan-repair path §2.6 and SDD-PAY-002 §2.3/§7 designate — the repair deallocation carries `InvoiceSettledAmount = 0.00`, which one rule said to apply and the other said to ignore. §2.14 is now scoped to the TRANSITION (cancel and reverse write no settlement column, so no history is rewritten) and defers explicitly to §2.15 for what later events do; §2.15 applies them, so the mirror stops claiming released cash and the repair actually lands. Pinned by §6.7 `AllocationConsumer_DeallocationAfterCancel_ZeroesSettledAmount_AndRederivesStatus`. Freezing the columns at the terminal transition was rejected: it would leave the invoice permanently reporting cash `finance_payments` no longer holds and would silently disable the only repair path the two specs offer.
- **The invoice carries its OWN frozen booking rate — RESOLVED: a dedicated column in the same migration.** Before this amendment the aggregate had `CurrencyCode` and `BaseCurrencyCode` but no rate, so `InvoiceConfirmedEvent.BookingExchangeRate` had no source and could only have carried a fabricated `1.000000` — corrupting SDD-PAY-002's `RealizedFxDifference` and SDD-PAY-003's `BaseOutstanding` for every non-base-currency invoice. `ExchangeRate` (`DECIMAL(18,6) NOT NULL` default `1.000000`) therefore shipped in the SAME additive `20260805182742_AddInvoiceSettlement` migration (`Invoice.cs:60`), frozen at creation exactly as `BaseCurrencyCode` is, and is the sole source of the event field (§2.14/§2.15) — pinned by `CreateDraft_FreezesCallerSuppliedExchangeRate_ForNonBaseCurrencyInvoice`, `UpdateDraft_DoesNotChangeTheFrozenExchangeRate` and `Confirm_NonBaseCurrencyInvoice_PublishesItsRealBookingExchangeRate_NotOne` (§6.7). Cross-rate allocation stays LEGAL — SDD-PAY-002 computes the realized difference for real against a dormant posting seam; no `PAYMENT_ALLOCATION_FX_UNSUPPORTED`-style rejection is introduced on either side.
- **Invoice reversal is PUBLISHED, never silent — RESOLVED: `InvoiceReversedEvent` shipped in Batch 17.** Before this amendment `src/Finance.ServiceModel/Events/Invoices/` held only `InvoiceConfirmedEvent`, `InvoiceCancelledEvent`, and `InvoicePostedEvent` (verified), so a `Reversed` invoice was invisible outside this service. That is not merely a mis-aging nuisance: SDD-PAY-002 §2.5 admits open items whose mirrored `InvoiceStatus` is `Confirmed` or `Posted`, so a reversed SaleInvoice — whose GL effect is fully offset — would stay a LEGAL allocation target, letting an operator match real cash against a document with no remaining ledger balance while the genuinely open invoice stayed outstanding. Publishing the event from the §2.7 transition (§2.11) let SDD-PAY-002 register its consumer and exclude `Reversed` from eligibility in the SAME batch. This SUPERSEDES the earlier decision to defer the event and merely record the projection blind spot as an open item. The transition itself is unchanged; only the publish was added — and it ships as `MarkReversedAsync`, which nothing invokes in production yet because the automatic full-offset detection and its endpoint stay deferred (§5).
- **One posted journal entry per invoice — RESOLVED: a source-document link on `JournalEntry` (SDD-PAY-001 item, recorded here because §2.5 owns the handshake it hardens).** Before Batch 17 the `InvoiceConfirmedEventConsumer` posted unconditionally and `JournalEntry` carried no source-document reference (only `ReversesEntryId`) — both verified — so its only protection against a duplicate post was `IdempotencyFilter<T>`'s 7-day `MessageId` claim, which EXPIRES and does not survive a `finance-journal_error` replay. The consumer therefore gained source-document stamping plus, for an already-`Posted` `("Invoice", InvoiceId)` pair, a path that posts nothing and re-publishes `InvoicePostedEvent` for the existing entry (§2.5) — backed by the additive `JournalEntry` columns, the `20260805174405_AddJournalEntrySourceDocument` migration and the UNIQUE FILTERED index that SDD-PAY-001 §2.5 owns and applies identically to `("Payment", PaymentId)`. The re-publish rather than a silent return was chosen deliberately: the invoice-side consumer is already idempotent, so re-emitting the back-event costs nothing and recovers the case where the FIRST back-event was lost after the entry had been posted. Relying on the Redis claim alone was rejected: a post-TTL redelivery overstates the control account while the trial balance still balances and this service still shows one linked entry, which makes the error invisible to every existing check. The invoice-side effect is nil — the aggregate, its states, its events and the handshake steps are untouched.
- **Shared settlement enum — RESOLVED: ONE enum, owned by SDD-PAY-002 §2.8.** The type is `SettlementStatus` (`src/Finance.Common/Enums/SettlementStatus.cs`, `Unsettled = 1`, `PartiallySettled = 2`, `Settled = 3`), DECLARED and OWNED by SDD-PAY-002 §2.8 as the single owner. This spec CONSUMES it: the property stays `Invoice.SettlementStatus` and no `InvoiceSettlementStatus` type is declared here. The shorter name is correct because settlement is not invoice-specific, and because SDD-PAY-002's allocation events already carry a PROPERTY named `InvoiceSettlementStatus` (§2.15 step 4) that would collide awkwardly with an identically-named type. Superseded the earlier "MUST converge before implementation" open item.
